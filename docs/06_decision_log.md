# 4. 초기 의사결정

## ADR-001 웹 기반 3D 게임으로 개발

- 상태: 승인
- 결정:
  - PC 웹 브라우저를 1차 플랫폼으로 사용한다.
  - Three.js를 렌더링 엔진으로 사용한다.
- 이유:
  - 설치 없이 URL로 접근할 수 있다.
  - 해커톤 시연과 배포가 쉽다.
  - 2인 온라인 접속 흐름을 빠르게 확인할 수 있다.
- 단점:
  - 네이티브 게임 엔진보다 애니메이션과 툴 지원이 제한적이다.
  - 브라우저별 성능 차이가 있다.
- 재검토 조건:
  - 목표 장면에서 30 FPS를 유지하지 못할 경우

## ADR-002 규칙 기반 링크 이동 보정

- 상태: 승인
- 결정:
  - 두 파이터 연결은 완전한 물리 Joint보다 이동 벡터 보정을 중심으로 구현한다.
- 이유:
  - Joint 기반 구현은 캐릭터 떨림과 폭발적인 반발 위험이 높다.
  - 온라인 서버에서 같은 결과를 재현하기 어렵다.
  - 핵심 목적은 사실적 물리보다 통제 가능한 협동 이동이다.
- 단점:
  - 실제 물리처럼 자연스러운 일부 장면이 줄어든다.
  - 보정 규칙을 직접 설계해야 한다.
- 검증:
  - 반대 방향 입력 30초 테스트
  - 벽 모서리 이동 테스트

## ADR-003 서버 권한형 게임 판정

- 상태: 승인
- 결정:
  - 위치, 공격, 데미지, 체력, AI, 승패는 서버가 최종 결정한다.
- 이유:
  - 두 클라이언트의 상태 불일치를 방지한다.
  - 공격과 체력 조작을 막는다.
  - AI 결과를 동일하게 유지한다.
- 단점:
  - 입력 지연이 체감될 수 있다.
  - 클라이언트 예측이 없으면 이동 반응성이 낮을 수 있다.
- 재검토:
  - 실제 외부 테스트에서 이동 지연이 심할 경우 제한적 클라이언트 예측 추가

## ADR-004 MVP는 2인 협동 대 AI

- 상태: 승인
- 결정:
  - 첫 MVP는 플레이어 2명 vs AI 2명으로 제한한다.
  - 4인 PvP는 제외한다.
- 이유:
  - 4인 동기화와 매칭 기능은 핵심 재미 검증에 필수적이지 않다.
  - 테스트 인원 모집 부담을 줄인다.
  - AI를 통해 반복 테스트가 가능하다.
- 단점:
  - 장기적인 경쟁 재미는 검증하지 못한다.

## ADR-005 한 명 다운 후 경기 지속

- 상태: 승인
- 결정:
  - 한 명의 체력이 0이어도 팀은 패배하지 않는다.
  - 남은 플레이어가 다운된 팀원을 끌고 싸운다.
- 이유:
  - 게임의 대표적인 코미디와 역전 상황을 만든다.
  - 개인 실수로 경기가 즉시 종료되는 문제를 줄인다.
- 단점:
  - 드래그 충돌과 상태 처리가 복잡해진다.

## ADR-006 카메라는 클라이언트 독립

- 상태: 승인
- 결정:
  - 카메라 위치와 회전은 네트워크로 동기화하지 않는다.
- 이유:
  - 각 플레이어가 원하는 시점을 사용할 수 있다.
  - 불필요한 네트워크 메시지를 줄인다.
  - 카메라는 경기 판정과 무관하다.

## ADR-007 손잡기는 팀 공용 능력

- 상태: 승인
- 결정:
  - 두 플레이어 중 한 명이 입력하면 팀 전체 링크가 손잡기 상태로 전환된다.
- 이유:
  - 두 플레이어가 동시에 버튼을 눌러야 하는 불필요한 실패를 줄인다.
  - 빠른 상황 대응이 가능하다.
- 위험:
  - 한 명이 팀원 의사와 무관하게 사용할 수 있다.
- 재검토:
  - 플레이테스트에서 갈등 요소가 강하면 동시 입력 또는 승인 방식 검토
