# 4. 초기 의사결정

## ADR-001 웹 기반 3D 게임으로 개발

- 상태: 승인
- 결정:
  - PC 웹 브라우저를 1차 플랫폼으로 사용한다.
  - Three.js를 렌더링 엔진으로 사용한다.
- 이유:
  - 설치 없이 URL로 접근할 수 있다.
  - 해커톤 시연과 배포가 쉽다.
  - 2인 온라인 접속 흐름을 빠르게 확인할 수 있다.
- 단점:
  - 네이티브 게임 엔진보다 애니메이션과 툴 지원이 제한적이다.
  - 브라우저별 성능 차이가 있다.
- 재검토 조건:
  - 목표 장면에서 30 FPS를 유지하지 못할 경우

## ADR-002 규칙 기반 링크 이동 보정

- 상태: 승인
- 결정:
  - 두 파이터 연결은 완전한 물리 Joint보다 이동 벡터 보정을 중심으로 구현한다.
- 이유:
  - Joint 기반 구현은 캐릭터 떨림과 폭발적인 반발 위험이 높다.
  - 온라인 서버에서 같은 결과를 재현하기 어렵다.
  - 핵심 목적은 사실적 물리보다 통제 가능한 협동 이동이다.
- 단점:
  - 실제 물리처럼 자연스러운 일부 장면이 줄어든다.
  - 보정 규칙을 직접 설계해야 한다.
- 검증:
  - 반대 방향 입력 30초 테스트
  - 벽 모서리 이동 테스트

## ADR-003 서버 권한형 게임 판정

- 상태: 승인
- 결정:
  - 위치, 공격, 데미지, 체력, AI, 승패는 서버가 최종 결정한다.
- 이유:
  - 두 클라이언트의 상태 불일치를 방지한다.
  - 공격과 체력 조작을 막는다.
  - AI 결과를 동일하게 유지한다.
- 단점:
  - 입력 지연이 체감될 수 있다.
  - 클라이언트 예측이 없으면 이동 반응성이 낮을 수 있다.
- 재검토:
  - 실제 외부 테스트에서 이동 지연이 심할 경우 제한적 클라이언트 예측 추가

## ADR-004 MVP는 2인 협동 대 AI

- 상태: 승인
- 결정:
  - 첫 MVP는 플레이어 2명 vs AI 2명으로 제한한다.
  - 4인 PvP는 제외한다.
- 이유:
  - 4인 동기화와 매칭 기능은 핵심 재미 검증에 필수적이지 않다.
  - 테스트 인원 모집 부담을 줄인다.
  - AI를 통해 반복 테스트가 가능하다.
- 단점:
  - 장기적인 경쟁 재미는 검증하지 못한다.

## ADR-005 한 명 다운 후 경기 지속

- 상태: 승인
- 결정:
  - 한 명의 체력이 0이어도 팀은 패배하지 않는다.
  - 남은 플레이어가 다운된 팀원을 끌고 싸운다.
- 이유:
  - 게임의 대표적인 코미디와 역전 상황을 만든다.
  - 개인 실수로 경기가 즉시 종료되는 문제를 줄인다.
- 단점:
  - 드래그 충돌과 상태 처리가 복잡해진다.

## ADR-006 카메라는 클라이언트 독립

- 상태: 승인
- 결정:
  - 카메라 위치와 회전은 네트워크로 동기화하지 않는다.
- 이유:
  - 각 플레이어가 원하는 시점을 사용할 수 있다.
  - 불필요한 네트워크 메시지를 줄인다.
  - 카메라는 경기 판정과 무관하다.

## ADR-007 손잡기는 팀 공용 능력

- 상태: 승인
- 결정:
  - 두 플레이어 중 한 명이 입력하면 팀 전체 링크가 손잡기 상태로 전환된다.
- 이유:
  - 두 플레이어가 동시에 버튼을 눌러야 하는 불필요한 실패를 줄인다.
  - 빠른 상황 대응이 가능하다.
- 위험:
  - 한 명이 팀원 의사와 무관하게 사용할 수 있다.
- 재검토:
  - 플레이테스트에서 갈등 요소가 강하면 동시 입력 또는 승인 방식 검토

## ADR-008 서버 물리 이전 전 위치 동기화 경계

- 날짜: 2026-07-31
- 참여자: 개발팀
- 상태: 승인(과도기, 서버 Rapier 이전 시 대체 예정)
- 배경:
  - 체력·다운·승패를 `combat_room`의 서버 권한 상태로 전환한 뒤 두 브라우저의 플레이어 위치도 동기화할 필요가 생겼다.
  - 현재 Rapier 월드와 캐릭터 컨트롤러는 클라이언트에만 존재한다.
- 해결해야 할 문제:
  - 서버가 Rapier 없이 계산한 위치를 모든 클라이언트 물리 객체에 강제 적용하자 플레이어가 적 콜라이더를 통과했다.
  - 소유 캐릭터 좌표의 강제 적용을 제거하자 경기 초기화 시 각 탭의 소유 캐릭터 위치가 달라졌다.
  - 위치 스냅샷 형식 변경이 이전 서버와 호환되지 않으면 같은 콜백의 HP·상태 반영까지 중단될 수 있었다.
- 검토한 선택지:
  1. 서버에서 단순 좌표와 링크 거리만 계산하고 모든 클라이언트에 강제 적용한다.
  2. 즉시 서버에 Rapier를 설치하고 이동·충돌 전체를 서버 권한으로 전환한다.
  3. 소유 클라이언트가 Rapier 충돌 계산을 수행하고 서버가 슬롯·순서·범위를 검증해 같은 룸에 중계한다.
- 결정:
  - 현재 스프린트에서는 선택지 3을 사용한다.
  - HP·다운·링크 상태·승패는 계속 서버가 최종 권한을 갖는다.
  - 위치는 배정된 소유 클라이언트가 계산하되 서버가 session-slot 소유권, sequence, 유한값, 경기장 범위, 최대 이동량을 검증한다.
  - 평상시 스냅샷은 원격 캐릭터에만 적용해 소유 캐릭터의 Rapier 충돌 결과를 보존한다.
  - 경기 초기화는 `resetRevision`을 증가시키고 모든 클라이언트가 소유 여부와 관계없이 동일한 초기 물리 좌표를 적용한다.
- 선택 이유:
  - 기존 충돌과 로컬 조작감을 회귀시키지 않으면서 두 탭 위치 공유를 검증할 수 있다.
  - 서버 물리 이전과 공격 서버 판정을 한 번에 수행하는 범위 증가를 피한다.
  - 과도기 권한 경계를 명시해 임시 구현이 최종 구조로 오해되는 것을 방지한다.
- 장점:
  - 기존 플레이어-적 Rapier 충돌을 유지한다.
  - 각 세션이 배정받은 파이터 위치만 보고할 수 있다.
  - 두 탭의 체력·상태·위치·초기화 결과를 같은 `combat_room` broadcast로 공유한다.
- 단점:
  - 악성 클라이언트가 허용 범위 안에서 좌표를 조작할 가능성이 남는다.
  - 두 소유 클라이언트의 동시 이동과 플레이어 간 충돌은 서버 물리만큼 결정적이지 않다.
  - 원격 좌표는 현재 teleport 기반이라 추후 스냅샷 보간이 필요하다.
- 영향 범위:
  - `CombatRoom`, `CombatNetwork`, `Arena`, 공용 전투 스냅샷 및 이벤트 타입
- 검증 방법:
  - 두 탭의 `Combat room` ID가 같은지 확인한다.
  - 한 탭에서 이동했을 때 반대 탭의 위치가 갱신되는지 확인한다.
  - 이동 중 플레이어가 고정된 적 콜라이더를 통과하지 않는지 확인한다.
  - DRAW 이후 한 탭에서 초기화했을 때 양쪽 HP, 상태, 색상, 네 파이터 위치가 일치하는지 확인한다.
  - 서버 종료 시 로컬 fallback이 유지되는지 확인한다.
- 재검토 조건:
  - 서버 Rapier 월드와 고정 tick 이동 계산을 도입할 때 선택지 2로 대체한다.
  - 100ms 이상 지연에서 원격 순간이동 또는 플레이어 간 겹침이 눈에 띌 때 보간·예측을 함께 설계한다.

  - `12_network_sync_troubleshooting.md`
  - `02_state_transition_spec.md` 8장 상태 동기화 원칙

# 6. 폐기된 아이디어 기록

폐기된 아이디어도 삭제하지 않고 이유를 기록한다.

| 아이디어 | 폐기 이유 | 재검토 조건 |

| 완전한 래그돌 다운 | 안정성과 네트워크 동기화 위험 | 물리 프로토타입이 안정화될 때 |

| 자동 매칭 | 방 코드로 충분 | 실제 사용자 유입 이후 |
